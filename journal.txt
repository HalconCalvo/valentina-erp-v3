## Todos los formularios, tablas y modales DEBEN usar estos componentes.

- VSearchSelect    — selector con búsqueda en tiempo real, autocomplete
- VInput           — input con validación, mensaje de error, estado loading
- VNumberInput     — numérico con formato moneda/cantidad, min/max, decimales
- VDatePicker      — selector de fecha con calendario, rango de fechas
- VTextArea        — área de texto con contador de caracteres
- VCheckbox        — checkbox con label, descripción y estado indeterminado
- VToggle          — switch on/off para estados booleanos
- VFileUpload      — carga de archivos con preview y validación de tipo/tamaño

- VSelect          — dropdown simple con opciones estáticas

## FLUJO DE CANCELACIÓN DE SOLICITUDES Y OCs

### Solicitud de compra:
- Cualquier rol puede cancelar SUS PROPIAS solicitudes
- Solo cancelable si la OC ligada NO ha sido enviada al proveedor
- Si ya existe OC ligada en BORRADOR o AUTORIZADA:
  → Notifica a ADMIN para que ajuste o cancele la OC
  → OC regresa a BORRADOR y requiere nueva autorización
- Si OC ya fue ENVIADA:
  → Producción/rol NO puede cancelar directamente
  → Debe notificar a ADMIN para gestionar con el proveedor

### Cancelación de OC enviada (proveedor acepta):
- ADMIN cancela la OC desde Valentina con motivo obligatorio
- Efectos automáticos al cancelar:
  1. OC queda en estado CANCELADA con fecha, usuario y motivo
  2. Solicitudes origen regresan a estado PENDIENTE
  3. Si había anticipo pagado → queda como saldo a favor del proveedor
  4. Si había factura de anticipo → se cancela y revierte el saldo
- ADMIN puede generar nueva OC corregida desde las solicitudes

### Regla general:
- Antes de enviarse al proveedor → error se corrige internamente
- Después de enviarse → requiere gestión con el proveedor y
  cancelación explícita en Valentina con motivo documentado

## PRINCIPIO: PREVER LO IMPREVISIBLE — APLICA A TODO VALENTINA

### La pregunta que el arquitecto debe hacerse en cada flujo:
"¿Qué pasa si algo sale mal en este punto?"

### Casos que SIEMPRE deben estar previstos:

#### Error humano de captura:
- ¿Se puede corregir antes de que tenga efecto externo?
- ¿Se puede corregir después de que tuvo efecto externo?
- ¿Qué se revierte automáticamente al corregir?

#### Cancelación por acuerdo entre partes:
- ¿Quién puede cancelar y en qué estados?
- ¿Qué efectos tiene la cancelación en saldos y registros ligados?
- ¿Qué queda como evidencia de la cancelación?

#### Error del proveedor o cliente:
- Proveedor factura mal → ¿cómo se corrige en Valentina?
- Cliente pide cambio de producto → ¿cómo afecta la OV y producción?
- Proveedor no entrega completo → ¿cómo queda el saldo pendiente?

#### Falla técnica o de proceso:
- ¿Qué pasa si se corta internet en medio de una recepción?
- ¿Qué pasa si se duplica accidentalmente un registro?
- ¿Qué pasa si dos usuarios editan el mismo registro al mismo tiempo?

#### Cambio de decisión:
- ¿Hasta qué punto se puede cambiar de opinión sin consecuencias?

### Regla de diseño resultante:

1. El camino feliz (todo sale bien)
2. El camino de corrección (error humano antes de efecto externo)

4. El camino de cancelación (acuerdo entre partes)

Sin estos 4 caminos definidos, el flujo NO se construye.

## ARQUITECTURA BACKEND — PLAN DE MIGRACIÓN (seguir al pie de la letra)

### El problema actual:

- Sin separación de responsabilidades

### La arquitectura objetivo (4 capas):
API Layer (endpoints)    — solo recibe peticiones y devuelve respuestas
    ↓
Service Layer (services) — toda la lógica de negocio vive aquí
    ↓
Repository Layer         — todo el acceso a datos vive aquí
    ↓
Database (PostgreSQL)    — solo datos

### Regla permanente:
Ningún código nuevo se escribe directamente en endpoints/.
Todo lo nuevo va en services/.
Los endpoints solo llaman al service y devuelven la respuesta.

### Plan de migración en 3 fases:

FASE 1 — Definir arquitectura objetivo en CLAUDE.md (HOY)
- Documentar las 4 capas y sus responsabilidades

- Crear carpetas services/ y repositories/ con archivos base
- Cursor sabe dónde debe ir cada cosa nueva

FASE 3 — Migración gradual por módulo (SESIONES SIGUIENTES)
- Cada vez que se toca un endpoint para agregar funcionalidad nueva,

6. Sin queries en loops — usar selectinload o joins

## PRINCIPIOS UX Y DE PROCESO — VALENTINA ERP
## (Nivel Oracle/SAP — universales, no negociables)

### 1. ORIENTADO A PROCESOS, NO A PANTALLAS
El sistema guía al usuario a través del proceso completo.
El usuario no busca funciones — el sistema le dice qué sigue.
Nunca diseñamos una pantalla sin primero definir el proceso completo
que esa pantalla soporta.

### 2. ROLES Y RESPONSABILIDADES CLAROS
Cada actor del proceso ve exactamente lo que necesita para hacer su parte.
Nada más, nada menos.
Si un usuario tiene que buscar algo que no le corresponde, el diseño está mal.

### 3. TRAZABILIDAD COMPLETA
Cada acción queda registrada: quién hizo qué, cuándo y por qué.
Auditable en cualquier momento.
Aplica a: facturas, pagos, cambios de estado, cancelaciones, correcciones.

### 4. ALERTAS PROACTIVAS
El sistema avisa cuando algo requiere atención.
No espera a que el usuario lo descubra.
Cada rol tiene su panel de alertas con acciones pendientes.

### 5. CONSISTENCIA TOTAL
Mismo patrón visual y de interacción en todo el sistema.
Si el usuario aprende a usar un módulo, sabe usar todos.
Mismos componentes, mismos colores de estado, mismos flujos de confirmación.

### 6. DATOS EN TIEMPO REAL
Los números que el usuario ve reflejan el estado actual del negocio.
Sin necesidad de refrescar manualmente.
Sin inconsistencias entre módulos.

### 7. ACCESO DIRECTO A ENTIDADES
Cada entidad importante tiene su propia pantalla accesible desde el menú.
Las facturas no viven dentro de Rayos X.
Los pagos no viven dentro de un modal de OV.
Máximo 3 clics para llegar a cualquier acción.

### 8. EL CONTEXTO NO SE PIERDE
Si el usuario está viendo una OV y emite una factura,
al terminar regresa a la misma OV — no al inicio del módulo.
Las acciones fluyen sin interrumpir el contexto de trabajo.

### 9. VALIDACIÓN ANTES DE PERMITIR
El sistema no permite avanzar si faltan datos críticos.
No errores después — validación en el momento correcto del proceso.
Mensajes claros de qué falta y por qué.

### 10. EL PROCESO DEFINE LA PANTALLA
Antes de diseñar cualquier pantalla, se define:
  - ¿Quién inicia este proceso?
  - ¿Qué información necesita cada actor?
  - ¿Quién aprueba, quién ejecuta, quién supervisa?
  - ¿Qué pasa si hay un error en cualquier punto?
  - ¿Cómo sabe el sistema que el proceso terminó correctamente?

### REGLA DE ORO DEL DISEÑO:
Si un usuario tiene que buscar algo, el diseño falló.
El sistema debe presentar la información correcta
al usuario correcto en el momento correcto.

## SESIÓN 2026-08-31 (tarde) — Bug folio duplicado en rollback
### Problema:
Al revertir una recepción completa, accounts_payable quedaba en status
CANCELADO en vez de eliminarse. El folio quedaba ocupado y al reutilizarlo
el candado (status != 'CANCELADO') no lo detectaba como duplicado.
### Solución aplicada:
Cuando _nuevo_total <= 0.01 en la corrección de recepción:
- DELETE purchase_invoices WHERE accounts_payable_id = ap_id (primero)
- DELETE accounts_payable WHERE id = ap_id (después)
Cuando _nuevo_total > 0.01: UPDATE con status = PENDIENTE fijo (sin CANCELADO).

## DECISIÓN ESTRATÉGICA — VALENTINA COMO PRODUCTO SaaS (2026-09-08)

### Decisión de Gabriel:
Valentina se desarrollará para venderse como producto SaaS a otras empresas
de manufactura a la medida (cocinas, closets, etc.)

### Implicaciones arquitectónicas:
Para convertir Valentina en un producto SaaS multi-tenant se requiere:

1. company_id en todos los modelos de datos
   Cada tabla necesita un campo company_id para separar datos entre empresas.
   Esto afecta: clients, sales_orders, purchase_orders, materials,
   users, quotations, inventory, treasury, etc.

2. Sistema de autenticación por empresa
   - Registro de empresas (tenants)
   - Login que identifica a qué empresa pertenece el usuario
   - Tokens JWT con company_id embebido

3. Middleware de aislamiento
   Cada query automáticamente filtra por company_id del usuario autenticado.
   Ninguna empresa puede ver datos de otra.

4. Panel de administración central (super-admin)
   Para gestionar empresas, suscripciones, límites de uso.

5. Configuración por empresa
   GlobalConfig, tax_rates, roles, etc. — uno por empresa.

### Estrategia recomendada:
NO hacer el cambio ahora — hacerlo al momento del arranque en ceros.
Cuando Valentina reinicie limpia, implementar multi-tenancy desde el día 1.
Koloka será el primer tenant (empresa #1).

### Fase nueva — FASE 11: Multi-Tenancy SaaS
Agregar al plan maestro después de la Fase 10.
Estimación: 6-8 semanas de trabajo adicional.
Requiere: Fase 9 (Seguridad) completada primero.

### Por ahora:
Continuar con el plan actual. Al momento del arranque en ceros,
ejecutar la transformación a multi-tenant antes de reiniciar.
